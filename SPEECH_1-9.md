## Слайд 1. Титульный — EVRAZ Agent

Добрый день, уважаемая аудитория!

Представляю вам наш проект — **EVRAZ Agent**: AI-агент для интеллектуальной работы с Excel-файлами металлургической компании.

Это система «вопрос–ответ»: она забирает на себя рутинную работу с таблицами и позволяет бизнес-пользователям получать нужные данные, просто задавая вопрос на обычном языке.

Стек проекта: на бэкенде — Python 3.12, FastAPI, LangGraph и PostgreSQL; на фронтенде — React 18 с TypeScript и Vite. О деталях — дальше по ходу презентации.

## Слайд 2. Контекст — Проблематика

Начну с проблемы, ради которой всё это делается.

Наша компания каждый день получает Excel-файлы с ценами на цветные металлы — в первую очередь на лом. Это десятки листов в каждом файле, и форматы постоянно отличаются друг от друга.

Мало того, сами файлы «грязные»: шапки таблиц сдвинуты, ячейки объединены, заголовки вложенные. Разобраться в такой структуре автоматически — нетривиальная задача.

При этом бизнес-пользователи не хотят и не должны разбираться в устройстве таблиц. Они хотят задавать вопрос простым языком — и получать ответ.

И ещё один важный момент: цены — это коммерческая тайна. Данные категорически не должны утекать наружу, поэтому мы не можем использовать внешние сервисы для обработки этих файлов.

В итоге сегодня менеджер тратит часы на ручной поиск по файлам — вместо того, чтобы принимать решения.

---

## Слайд 3. Цель проекта — Задача

Наша задача — построить prod-ready систему «вопрос–ответ» по данным Excel.

Сценарий работы выглядит так:

1. Пользователь **загрузил файл** — и система сама его распарсила и нормализовала.
2. Пользователь **задал вопрос** на естественном языке — и получил ответ с данными.
3. Ответ **прозрачен**: видно, какой SQL был выполнен и откуда взялись цифры.
4. И всё это **безопасно**: только чтение, только проверенные таблицы, никакой утечки данных.

Ключевой критерий качества: точность не ниже **85%** на ключевых типах запросов — при полной traceability, то есть прослеживаемости каждого ответа.

## Слайд 4. Архитектура — Решение, обзор

Как устроено решение в целом.

Сверху — поток данных: Excel-файл попадает на парсинг, превращается в RAW-таблицы, затем нормализуется в витрину данных — mart. Это структурированное хранилище, с которым уже легко работать.

Снизу — поток вопросов: пользователь задаёт вопрос, LangGraph-агент планирует и выполняет безопасный SQL-запрос к витрине, и возвращает пользователю ответ вместе с SQL и источниками данных.

Проект состоит из трёх частей:

- **Бэкенд** — FastAPI, LangGraph, SQLAlchemy: API, парсинг и сам агент.
- **Фронтенд** — React 18, TypeScript, Vite: чат, файлы, дашборд, метрики, трейсы.
- **Инфраструктура** — Docker Compose и Nginx: PostgreSQL, Prometheus и Grafana.

## Слайд 5. Pipeline — Поток обработки файла

Теперь подробнее о том, как обрабатывается файл — это конвейер из пяти шагов.

**Первый шаг — Upload.** Пользователь загружает файл, система сохраняет его и ставит статус «uploaded».

**Второй — Ingestion.** Асинхронно запускается парсинг Excel: извлекаются листы, колонки, ячейки и даже комментарии.

**Третий — Schema Inference.** Для новых, незнакомых форматов LLM предлагает схему. А известные форматы распознаются по «Template Fingerprint» — цифровому отпечатку шаблона — вообще без участия модели. Это быстро и дёшево.

**Четвёртый — Normalize.** Данные переносятся в витрину. Перенос идемпотентный: повторная заливка файла не создаёт дублей.

**Пятый — Entity Resolution.** Собираются справочники сущностей — названий, поставщиков, периодов — которые дальше понадобятся агенту для точных ответов.

Итоговая цепочка состояний: `uploaded → processing → ready`, либо `failed` с понятным текстом ошибки.

## Слайд 6. Данные — Витрина данных (mart)

Ключ к простому агенту — правильные данные. Поэтому мы строим витрину из long-факт-таблиц.

Первая таблица — `mart.price_facts`: цены лома. Здесь `sheet_period` — период листа, например, январь 2025-го; `item_name` — название позиции, например, «Лом меди марки А»; `supplier` — поставщик; `price_type` — тип цены: среднерыночная, старт аукциона или цена поставщика; значения с валютой и единицей измерения; и отдельный флаг `is_blank` — пустая ячейка не превращается молча в ноль.

Вторая таблица — `mart.metrics`: производственные метрики. Та же идея: измерение, период, тип метрики, значение.

Почему это важно: благодаря long-факт-формату агент генерирует простой, понятный SQL — ему не нужно обращаться к сырым ячейкам.

## Слайд 7. Ядро системы — LangGraph-агент

Сердце системы — агент на LangGraph: граф из семи узлов, с чекпоинтами в PostgreSQL и ретраями.

Разберу по шагам:

- **Classifier** — определяет тип запроса: lookup, агрегат, сравнение, сводка по листам — и домен: цены или метрики.
- **Disambiguation** — при необходимости уточняет вопрос: либо прерывает пользователя, либо разрешает неоднозначность автоматически.
- **Planner** — составляет текстовый план действий.
- **CodeGen** — генерирует SQL, применяет детерминированные правки и валидирует результат.
- **Executor** — выполняет read-only запрос; если результат пустой — запускает fallback-запрос.
- **Verifier** — LLM проверяет корректность: до трёх попыток с детерминированным запасным вариантом.
- **Answer** — формирует финальный ответ на естественном языке.

У каждого ответа есть уровень уверенности: `success` — выше 0,7, `low_confidence` — агент сам исправляется, и `failed`.

## Слайд 8. Безопасность SQL — Безопасная генерация SQL

Отдельно остановлюсь на безопасности генерации SQL — потому что агент имеет доступ к живым данным.

Во-первых, детерминированные правки в CodeGen. Например, запрос «все виды меди» превращается в префиксный фильтр `item_name ILIKE 'Лом меди%'`. Поставщик «Сплав-21» нормализуется в паттерн `%сплав21%`. Булевы поля приводятся к 0 и 1. Всё это — стабильные правила, а не «фантазия» модели.

Во-вторых, у нас есть альтернатива LLM — модуль `sql_compiler.py`: он компилирует структурированную спецификацию запроса в безопасный SELECT напрямую, без модели.

В-третьих, обязательная валидация перед выполнением: только SELECT и только таблицы из whitelist `mart.*`; запрещены INSERT, UPDATE, DELETE, DROP, ALTER; проверяется баланс скобок и кавычек, чтобы отсечь обрезанный SQL; и стоит жёсткий таймаут — 30 секунд.

Таким образом, даже при сбое модели агент физически не сможет изменить данные.

## Слайд 9. Интерфейс — Frontend (React + TypeScript)

И наконец — то, что видит пользователь: современный интерфейс на React и TypeScript.

Пять основных страниц:

- **Чат** — вопросы к агенту, индикатор прогресса по шагам графа, блок с выполненным SQL, таблица или график результата и модальное окно источников.
- **Файлы** — загрузка Excel, статусы обработки, просмотр листов и структуры файла.
- **Дашборд** — общая панель состояния системы.
- **Метрики** — Prometheus-метрики, в том числе latency отдельных узлов агента.
- **Трейсы** — пошаговый просмотр выполнения графа по каждому запросу.

Под капотом — переиспользуемые компоненты: AgentProgress, ChatMessage, ResultChart на Chart.js, ResultTable, SourcesModal, SqlBlock, TypingIndicator, SheetViewer, FileUpload и другие.
